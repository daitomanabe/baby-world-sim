# AI_WORKFLOW（GitHubを見ながらAIで更新し続ける運用設計）

## 0. 前提（現実）
AIは「リポジトリ全体を常時監視して勝手に更新」できない。
代わりに、**人間が“更新したい単位”を切り出し、AIに渡し、提案をPRに落とす**運用が現実的。

本書はそのための手順（運用・自動化の設計）をまとめる。

---

## 1. 推奨運用（最小構成）
### 1.1 役割
- Human（Maintainer）
  - 課題をIssue化し、受け入れ条件を定義する
  - AIの提案をレビューして採用する
- AI（提案者）
  - Issue内容 + 関連ファイルを読み、パッチ案を作る
  - 出典が必要な箇所はREFERENCESに追記する提案を行う

### 1.2 ループ（人間主導）
1. Issueを立てる（小さく分割）
2. `scripts/context_pack.mjs` で必要ファイルだけ束ねる
3. AIに「Issue + context」を渡す
4. AIが「差分（unified diff）」または「変更ファイル一式」を返す
5. Humanがブランチに適用し、PRを作成
6. CIを通し、レビューしてマージ

---

## 2. 自動化（GitHub Actionsを使う場合：設計）
### 2.1 目標
- Issueに `ai-ready` ラベルが付いたら、
  - コンテキストを作成（artifact）
  - AIを呼び出してパッチを生成
  - 自動でPRを作成
までを自動化する（※自動マージはしない）

### 2.2 セキュリティ
- APIキーは GitHub Secrets に置く
- 実行トリガーは `workflow_dispatch` と `issue_comment` などに限定し、乱用を防ぐ
- 生成パッチは必ずPRとしてレビューする（直pushしない）

### 2.3 このリポジトリに含まれるもの
- `.github/workflows/ai_pr.placeholder.yml`：プレースホルダー（未完成）
- `scripts/context_pack.mjs`：AIへ渡すファイル束ね

---

## 3. “AIに渡すコンテキスト”の作り方
### 3.1 なぜ必要か
LLMは巨大なリポジトリ全体を毎回読むのが苦手。
**必要なものだけ**を渡すことで精度が上がる。

### 3.2 推奨セット
- 該当コンポーネント（例：`src/features/simulation/VisualSimCanvas.tsx`）
- データモデル（例：`src/types.ts` / `src/data/*.json`）
- 設計書の該当セクション（`docs/TECHNICAL_DESIGN.md`）
- 受け入れ条件（Issue本文）

### 3.3 `context_pack` の方針
- サイズ制限を超えそうなら「重要ファイル優先」
- 出力に `tree.txt` と `diff.txt` を含める（将来）
- artifactとしてGitHubに保存できる形にする

---

## 4. レビュー基準（AIの提案を採用するか）
- 受け入れ条件を満たしているか
- 「断定表現」「診断っぽい表現」になっていないか
- 出典リンクと証拠レベルが適切か
- 変更が最小で、読みやすいか
- テスト/ビルドが通るか

---

## 5. 失敗パターン（避ける）
- Issueが大きすぎて、AIが雑にまとめる
- 出典が曖昧なままUIに出してしまう
- “週ごとの変化”を根拠ある事実として断定してしまう
- 自動マージで壊す（絶対NG）
